# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A MATLAB/Simulink (R2024a) mobile intrusion detection system. One Simulink app is deployed to two Android phones; a Button picks the role at runtime (released = Security Node, pressed = Monitoring Console). The phones talk over UDP on the same Wi-Fi. `README.md` has the operator-facing build/deploy steps; `PROJECT_GUIDE.md` is the long-form explanation (block diagrams, protocol, file-by-file walkthrough, design decisions, limitations).

## Running MATLAB

MATLAB is at `C:\Program Files\MATLAB\R2024a\bin\matlab.exe`. Run things headlessly with `-batch`:

```
matlab -batch "cd('C:\Users\prana\Documents\MobileIntrusionDetection'); test_logic_units"
```

`_run.ps1 -cmd <matlab expr> -tag <name>` does the same in the background, writing a diary to `_log_<tag>.txt` and touching `_done_<tag>.txt` on completion (poll for the done file, then read the log). `_log_*`/`_done_*` files are disposable.

## Tests

- `test_logic_units` — 37 unit checks on the pure `.m` logic (node/console state machines, clock math, audio engine). Seconds, no Simulink. Run one check by editing/inspecting the relevant `add(results, name, pass)` block; there is no per-test runner.
- `run_harness_test` — rebuilds `ids_sim_harness.slx` via `build_sim_harness`, simulates 130 s of `ids_scenario` with two `SecurityCore` instances over a deterministic 20%-loss link (LCG, not `rand`), runs 13 requirement checks, writes `harness_timeline.png`. 2–4 minutes. Errors if any check fails. (The PNG export fails if the file is open/locked elsewhere — the checks still ran.)

Rule from the project guide: after changing `ids_params.m` or any logic file, run both suites before rebuilding the phone app.

## Building the app

- `build_android_model` → `ids_android_app.slx`. Options: `'PeerIP', '<other phone IP>'` (instead of broadcast), `'EnableTorch', false`, `'AllowStubs', true` (placeholder blocks when the Android support package is missing — produces `ids_android_app_stub.slx`, not deployable). The Simulink Support Package for Android Devices is installed on this machine (confirmed via `matlabshared.supportpkg.getInstalled`), so a real build should work. It has not been built or deployed to phones yet. Run `androidhwsetup` once before the first hardware deploy, and expect that some block parameter names may differ by package version (the builder prints a warning for any it can't set).
- `patch_android_torch('ids_android_app'[, false])` patches the generated Java to add camera-LED control via a `ToApp` hook; must be re-run after every Simulink rebuild.
- `make_alert_audio` converts `alert_message.wav` → `alert_message.mat` (embedded at codegen time via `coder.load`).

All `.slx` models are generated by scripts — edit the builder `.m` files, never the `.slx` directly. `slprj/`, `*.slxc` are build caches.

## Architecture

Layering (what's tested is what ships):

1. **Pure logic functions** with explicit state, `S = f(S, inputs)`: `node_step`/`node_init`, `console_step`/`console_init`, `audio_step`/`audio_init`, plus helpers (`packet_ok`, `wrap180`, `epoch_to_civil`). No `persistent` here — this is what makes unit testing and two-instance harnesses trivial.
2. **`SecurityCore` subsystem** (`build_security_core.m`): two MATLAB Function blocks whose source is set as strings through the Stateflow API (`sfroot ... Stateflow.EMChart ... ch.Script = code`). The Controller holds `persistent N C`, runs **both** `node_step` and `console_step` every tick with the inactive one given `active=false` (held in reset), and selects `tx` from the active role. AudioEngine holds `persistent A`. To change block code, edit the string literals in `build_security_core.m`.
3. **Wrappers**: `build_android_model.m` surrounds `SecurityCore` with Android sensor/UDP/UI blocks; `build_sim_harness.m` instantiates it twice (Phone_A, Phone_B) with scripted inputs from `ids_scenario` stored in the model workspace, a lossy `WiFi_Network` block, and Unit Delays to break the algebraic loop.

Key constraints and conventions:
- **All code must be Embedded Coder–compatible** (`%#codegen`): fixed sizes and types, no growing arrays, no changing a variable's type (create a new variable instead, e.g. `torchD` → `torch = int32(torchD)`). Core logic uses `double`; Android block outputs are cast to double in the wrapper.
- **`ids_params.m` is the single source of constants** (thresholds, timing in steps of `Ts = 0.1 s`, packet layout, command codes, `PAIR_ID`). It is baked in with `coder.const(ids_params())`. Don't hard-code numbers in logic files.
- `wall_clock.m` branches on `coder.target('MATLAB'|'Rtw')`: interpreter uses `host_epoch` (extrinsic during simulation), generated C calls `time()` via `coder.ceval`.
- **Protocol**: 16-double UDP datagrams, port 25000, word 1 = `MAGIC`, word 16 = `PAIR_ID` (filters own broadcasts and other groups). `TYPE_STATUS` node→console every 0.5 s heartbeat plus immediately on events; `TYPE_CMD` console→node carries a sequence number and is re-sent each heartbeat until the node's status echoes that seq. Commands are idempotent per seq. Node states: `DISARMED → ARMING (exit delay, baseline learnt) → ARMED → ALARM` (latched). Breach cause bitmask: light=1, tilt=2, motion=4, link-lost=8 (console-side).
- Adding a command: `CMD_` code in `ids_params.m` → handle in `node_step.m` → send from `console_step.m` → Button in `build_android_model.m` → unit test → both suites.

Code comments are written for a reader coming from Python/C++ (explaining MATLAB idioms); keep that style when adding code.
